The problem

When a Kubernetes workload fails, an operator manually checks: pod status → events → container logs → node → deployment → service → PVC → ConfigMap/Secret — and only then forms a root cause. "Why isn't my application starting?" cannot be answered from pod status alone.

The same symptom has many causes. Pod = CrashLoopBackOff could mean: application exit code 1, OOMKilled, liveness probe failure, configuration error, dependency failure, init container failure. So a fixed rule like if CrashLoopBackOff → application crashed is unreliable.

2

Our goal

A system where the user asks a natural question, and the AI decides what to investigate — then real Kubernetes evidence is collected and the AI reasons over that evidence.

User question
   ↓
AI understands intent
   ↓
AI selects tools
   ↓
Tools collect REAL Kubernetes evidence
   ↓
Evidence back to AI
   ↓
AI correlates
   ↓
Grounded diagnosis

Key rule: AI does not invent Kubernetes facts. Kubernetes provides the facts; AI reasons over them.

3

Why Needle 3?

Needle 3 is the investigation brain. Its job is NOT to talk to Kubernetes directly. Instead:

Needle 3 → "I need pod status" → Go tool → Kubernetes API
Kubernetes evidence → Needle 3 → "Now I need pod events" → Go tool → ...

Needle 3 = brain. Kubernetes tools = hands/investigators. Go dispatcher and provider do the execution.

4

Why not just hard-coded rules?

Deterministic rules are reliable when the signal is explicit: OOMKilled → memory, ImagePullBackOff → image, Node NotReady → node. But as combinations grow, an if/else if rule engine becomes huge and brittle.

So the final architecture is hybrid:

            Kubernetes
                ↓
        Trusted evidence
                ↓
        Deterministic signals
                ↓
        ┌────────┴────────┐
        ↓                 ↓
   Clear cause      Ambiguous case
        ↓                 ↓
 Direct diagnosis    Needle 3
                         ↓
                 more investigation
                         ↓
                   correlation
                         ↓
                    diagnosis

Simple PM explanation: "We don't use AI to determine facts Kubernetes already knows. We use AI to reason over facts that are difficult to correlate."

Provider abstraction

Major architectural decision: no direct Kubernetes API calls scattered in Go code.

Diagnostic Tool → InfrastructureProvider → Kubernetes

InfrastructureProvider
  ├── LocalKubernetesProvider   (real cluster, KUBECONFIG-aware)
  ├── FakeProvider              (tests / offline demo)
  └── Stack8sProvider           (future)

Today: Local provider tests against real Kubernetes. Tomorrow: Stack8s provider connects to Stack8s infra APIs — the AI doesn't change.

Go's role: Needle = reasoning; Go = execution (validate tool name + arguments → dispatcher → provider → Kubernetes API). Provider stays read-only.

What the model actually receives + the loop

The UI already knows the target. The runtime passes it explicitly — the model must never guess the pod from the question:

Target namespace: ai-diagnose-test
Target pod: demo-image-failure
User question: Why isn't this pod starting?

Needle then:

get_pod_status → evidence: Pending, ErrImagePull
→ get_pod_events → Failed to pull image / BackOff
→ conclude: Kubernetes cannot pull the image.

The loop is bounded: if root cause is proven it stops; if evidence is insufficient it says so — it never guesses.

Container discovery (important bug fix)

Pod multi-container-test contains app + failing-sidecar. Only the sidecar fails. Pod name ≠ container name — the loop discovers real container names from get_pod_status before calling get_container_logs.

12

Error handling

  • RESOURCE_NOT_FOUND — the requested resource does not exist/is not visible. Loop stops, diagnosis states it was not found, no invented root cause.
  • COLLECTION_FAILED — Kubernetes evidence unavailable. Output: "Cannot determine diagnosis because Kubernetes evidence is unavailable." Never "Workload failure detected."

Evidence integrity: final diagnosis may only claim what tools returned. If evidence contains exit code 1, BackOff, and "Application crashed", the allowed claim is "application is repeatedly crashing" — not "database connection failed" unless database evidence exists.

13

Training story (important honesty)

Early version F19 baseline metrics: exact tool-call 63.5%, tool selection 76.2%, argument 87.7%. After tuning: 74.6% / 88.9% / 93.8%.

Then Dataset V3 was trained (383/97/68, 3450 steps, loss ≈ 0.0001, validation ≈ 0.0174) — but the real benchmark regressed badly: exact tool-call 8.82%, tool selection 33.8%, arguments 28.7%, errors mostly MISSING_TOOL.

Engineering lesson

Training loss ≠ production readiness. We benchmarked actual behavior and kept the validated Needle 3 F19 checkpoint for the runtime, not the regressed V3 model.

Runtime loads the model once (stateless=True per request so no state leaks between pods/namespaces), with a fixed 1280-token JAX JIT buffer for fast CPU inference.

Testing & lessons

go test -v ./...
go vet ./...
venv/bin/python3 -m unittest runtime.test_diagnostic_loop -v   # 41 tests

Lessons

  • Don't trust model output as ground truth — kubectl describe first, compare AI against ground truth.
  • Training metrics are not enough — benchmark actual tool-use behavior.
  • Never hardcode scenarios — discover namespaces/pods/containers/nodes dynamically.
  • Never let AI invent Kubernetes facts — Kubernetes is source of truth, Needle is reasoning.
16

What this is NOT + limits

Not a magic Kubernetes chatbot, not a replacement for kubectl, and not a hardcoded Q&A. It is an evidence-driven investigation system: Needle 3 decides what to investigate, Go executes, Kubernetes supplies facts, diagnosis is produced from those facts.

No automatic remediation yet — diagnosis and repair are separate for safety. Roadmap: Phase 1 diagnosis → Phase 2 incident correlation → Phase 3 suggested remediation → Phase 4 controlled remediation → Phase 5 autonomous SRE.

  • GPU data is capacity/allocation, not live DCGM utilization.
  • Endpoint readiness via events; no EndpointSlice tool yet.
  • RBAC surface currently returns provider errors only.

PM Q&A cheat sheet

"What did you build?" — An evidence-driven AI diagnostic system for Kubernetes. The user describes the problem; Needle 3 picks tools; Go runs them against the real cluster; Needle correlates the returned facts into a grounded diagnosis. AI never invents facts — Kubernetes is the source of truth.

"What was the model trained on?" — Needle 3 was LoRA fine-tuned on tool-use examples: question → tool call → evidence → next tool → grounded diagnosis. Dataset V3 has 548 audited examples (383 train / 97 val / 68 test) from controlled failures, synthetic tests, and docs. Training focused on tool selection, correct arguments, and multi-step diagnostic flows.

"When does the model see real data?" — At runtime. User question + explicit target + live evidence from the Go provider; final diagnosis is built only from that live evidence.

"Why need AI at all?" — Deterministic rules reliably catch explicit signals. AI's value is ambiguous/multi-resource correlation: CrashLoopBackOff alone is not a root cause — AI investigates state, events, logs, probes, config, and workload dynamically to find the real cause.

"Is it like AWS Agent SRE?" — Conceptually related, but Stack8s-native and cloud-agnostic. Stack8s already manages multi-cloud Kubernetes, so AI Diagnose plugs the diagnosis capability directly into that existing workflow.
