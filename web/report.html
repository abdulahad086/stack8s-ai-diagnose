PROJECT REPORT

AI Diagnose for stack8s

AI Diagnose is an AI-driven Kubernetes diagnostic system for Stack8s clusters. It turns a natural-language question about a namespace/pod into a grounded, evidence-backed diagnosis — collecting real cluster state via a provider boundary, attributing root causes correctly, and never inventing facts.

Go · Python · Needle 3 F19 · client-go · KORDIN-style UI

MODEL

What model we use & how it was built

Needle 3 — F19

Needle 3 is a small JAX-based language model. The F19 checkpoint (checkpoints/needle3.safetensors, ~231 MB) is the validated production model used at runtime; it was fine-tuned, not trained from scratch.

Training data

Built from real cluster incidents collected with the deterministic pipeline (F1–F15): pod status, events, logs, node/GPU/service/storage/workload/config evidence. Each record follows the official Needle JSONL schema (question → tool calls → evidence → grounded diagnosis), with secrets redacted, no leakage between train/validation/test pod contexts, and split 63% / 18.5% / 18.5%.

Fine-tuning

LoRA adapters trained on Kaggle T4 via feature19_needle3_kaggle.ipynb (10 epochs on dataset/train.jsonl), then exported to the single safetensors checkpoint used at runtime. Evaluation used the holdout test split and the benchmark.py tooling.

What the model sees at runtime

A compact prompt: the user question, the explicit target (namespace/pod), the tool JSON schema, and a bounded summary (~2000 chars) of the real provider evidence collected in Phase 2. It does not see kubeconfig, credentials, or secrets. Runtime buffer is fixed at 1280 tokens for fast CPU inference; JAX JIT is warmed up once at server start (~30–60s).

DESIGN RATIONALE

Why this architecture was chosen

  • Small LLM + deterministic orchestration. Needle 3 is good at language, not at cluster truth. So all truth comes from the InfrastructureProvider; the model only rephrases/frames evidence. This is what makes the system hallucination-resistant.
  • Intent-aware deterministic planning. Tool choice is computed from question intent (not left to the model), so the right tools run every time — GPU questions get GPU tools, not CrashLoop noise.
  • Causal evidence hierarchy. Specific causal evidence (termination reason, exit code, FailedScheduling, CreateContainerConfigError, probe events) outranks generic pod phase, so Pending/CrashLoopBackOff are never assumed to equal their common causes.
  • Provider boundary. One interface isolates client-go from reasoning, enabling Fake provider tests and a future Stack8s provider with zero reasoning changes.
  • Fail closed. Missing resources, provider errors, and empty results produce honest answers, never invented diagnoses.
  • Compare to a deterministic script. Scripts encode one answer per scenario; this system handles arbitrary namespaces/pods/questions because the reasoning layer is generic and the model only sees real, current evidence.
ARCHITECTURE

System

  • Web UI / API (runtime/server.py) — serves the UI, POST /api/diagnose, polls /api/diagnose/status.
  • Diagnostic loop (runtime/diagnostic_loop.py) — intent analysis → deterministic tool plan → bridge → grounded synthesis.
  • Tool executor (cmd/tool_exec) — JSON in/out per tool call, JSON out, prints provider target.
  • Dispatcher (provider/dispatcher.go) — validates ToolCall, routes to provider methods (9 tools).
  • InfrastructureProvider — boundary interface (22 methods); implementations: LocalKubernetes (client-go, only K8s imports), Fake (tests), Stack8s (future).
  • Needle 3 F19 — fine-tuned small LLM (checkpoints/needle3.safetensors) used for tool-schema synthesis; runtime treats it as advisory while evidence rules decide.
RUNTIME FLOW

How a diagnosis happens

  1. User supplies namespace + pod + question (+ provider) — target is propagated explicitly, never inferred from the question.
  2. Phase 1: intent-aware deterministic plan selects relevant tools (pod status/events/logs only for crash questions; GPU/storage/service/config/workload/node for those domains).
  3. Phase 2: tools execute via cmd/tool_exec; container names and node names are discovered from evidence, never hardcoded. Pending/unscheduled pods skip log collection. RESOURCE_NOT_FOUND short-circuits the investigation.
  4. Bridge verifies the real cluster target (KUBECONFIG, e.g. the Stack8s endpoint) before Needle synthesis.
  5. Phase 3: causal synthesis ranks domain evidence first, then Pending→scheduled/unscheduled lattice, init containers, probes (liveness/readiness/startup distinctions), then crash/image/oom classification — citing evidence and recommending only from the proven cause.

EVIDENCE RULES

Accuracy & Safety

  • Diagnosis is grounded only in collected evidence — no fabricated error strings, exit codes, or events.
  • Absence of evidence ≠ evidence of absence: RESOURCE_NOT_FOUND stops the investigation; Kubernetes API errors yield "unable to collect evidence", never a confident diagnosis.
  • Symptoms vs causes: CrashLoopBackOff is investigated (termination reason/exit code/OOM/probe), not assumed to mean "application crashed". Pending never assumed to mean unscheduled. Liveness/startup vs readiness probes distinguished. Completed never reported as failure.
  • Empty results are honest: empty service list → "no services found", not a CrashLoop diagnosis.
  • Kiosk-safe: provider errors propagate as bounded error fields; bounded tool calls; no resource mutation.

How to use

export STACK8S_PROVIDER=local-kubernetes
python3 -m http.server 8080 --directory web   # or run runtime/server.py 8080

KNOWN LIMITS

Limitations

  • Readiness endpoint-removal reasoning is event-based; EndpointSlice not exposed by the 9 tools.
  • RBAC errors surface as provider errors; no dedicated RBAC tool.
  • GPU data is capacity/allocation, not live DCGM utilization.
  • Diagnostic mode is read-only — remediation is a separate step.
